# ApxInf Qwen3.8-27B evaluation v1

This directory is the machine-readable evaluation source of truth for the
RTX 4090 summer-camp assignment. The scoring model is:

```text
100-point base leaderboard
  = correctness 30 + TTFT 35 + TPOT 25 + reliability 10

20-point optional bonus
  = context beyond 32K 10 + multi-request goodput 10

maximum displayed leaderboard score = 120
```

The base task remains deliberately narrow: one RTX 4090, the pinned
Qwen3.8-27B AWQ INT4 checkpoint, one text request at a time, deterministic
greedy decode, exact pre-tokenized input IDs, and client-observed timing. Long
context and multi-request serving are valuable extensions, but they no longer
distort the single-request base metric.

The current teacher implementation, model deployment details, and hidden data
are not part of the student handout. Students submit a PR against the public
ApxInf interfaces. Final JSON artifacts are generated by the teacher runner;
self-reported aggregate values are never accepted as official scores.

## Authoritative files

- `EXPERIMENT_REQUIREMENTS.md`: student-facing experiment stages, evidence,
  deliverables, and acceptance checklist derived from the contracts.
- `TEACHING_GUIDE.md`: instructor-facing introduction, demo sequence, slide
  outline, common questions, and disclosure boundaries.
- `SLIDE_OUTLINE.md`: page-by-page slide content, visual suggestions, speaker
  notes, appendices, and public-disclosure rules.
- `course-policy-v1.json`: seven-day schedule, day-4 midterm snapshot,
  workflow-innovation bonus, and final-report requirements. It does not change
  leaderboard cells or references.
- `contract-v1.json`: the only authority for workload cells, gates, weights,
  dynamic-reference policy, bonus rules, and course-grade mapping.
- `submission-schema-v1.json`: the runner-to-scorer exchange format.
- `score_submission.py`: a stdlib-only cohort scorer. Official scoring is a
  cohort operation, not an isolated submission operation.
- `compute_efficiency.py`: MFU/BWU proxy and optional profiler-counter
  calculator. Efficiency metrics are diagnostic and do not directly add score.
- `multimodal-contract-v1.json`: independently frozen image-input capability
  overlay. It cannot change the active text leaderboard score.
- `generate_multimodal_cases.py`, `run_multimodal.py`, and
  `score_multimodal.py`: deterministic public PNG generation, integrated chat
  execution, fail-closed checking, and capability-badge assignment.
- `test_*.py`: synthetic scorer tests and protocol negative controls. They do
  not contain teacher implementation results.

Runners and leaderboard pages must read the contract. They must not duplicate
weights, thresholds, or benchmark cells.

## Correctness: public and hidden

Correctness has a fixed public/hidden split before performance is considered.

| Split | Frozen coverage | Official points | Eligibility |
|---|---|---:|---:|
| protocol | request/stream/token-budget/error semantics | 5 | must pass |
| public functional | 1K early/middle/late retrieval plus 8K multi-hop, revision, and aggregate | 5 | 6/6 |
| hidden functional | retrieval 4, distractor 2, multi-hop 2, revision 2, aggregate 2; all at or below 16K | 15 | at least 11/12 |
| public token trajectory | 1K/128 and 8K/128, 256 reference tokens | 2 | evidence required; points are proportional |
| hidden token trajectory | two teacher prompts in the 2K–16K range, 256 reference tokens | 3 | evidence required; points are proportional |

Functional answers use deterministic, case-declared exact validators after
decoding with the pinned tokenizer, removing special tokens, and stripping
surrounding ASCII whitespace. There is no LLM judge. Token trajectories require
the complete output budget and use unit-cost Levenshtein edit similarity over
categorical token IDs against the frozen vLLM greedy reference. This preserves
insertions/deletions instead of turning one shifted token into every later
position being wrong; token IDs are never compared with MAE, cosine, embeddings,
or a semantic judge.

Public and hidden functional cases have a frozen 64-token maximum and may stop
on EOS after the exact answer. Only
performance, trajectory, context, and multi-request cells set `ignore_eos=true`
and require the complete 128-token budget.

The hidden contents, seeds, expected outputs, and manifest hash remain teacher
side. Before release, the teacher freezes those artifacts. During one
leaderboard round, neither public nor hidden case counts, categories, prompt
ceilings, budgets, validators, interfaces, or thresholds may change.

The public calibration profile has no hidden result. It reweights the visible
functional cases to preserve a 30-point visible correctness ceiling, so its
score is explicitly provisional and cannot be compared with an official
midterm snapshot.

Protocol, functional correctness, request success, and reliability are ranking
gates. Token trajectories remain correctness points and mandatory evidence,
but are not a performance-eligibility gate: the INT4 assignment does not claim
BF16-equivalent categorical generation at long context. An ineligible artifact
keeps a diagnostic breakdown, but `leaderboard_score` is `null` and it cannot
supply a TTFT, TPOT, or goodput champion reference.

## Dynamic TTFT and TPOT scoring

vLLM is a mandatory same-round control, not the definition of 100 points. For
each cell and metric, the scorer finds the best valid median among:

- the teacher-run vLLM control; and
- every correctness/reliability-eligible PR measured in the same frozen
  environment and leaderboard round.

Each candidate then receives:

```text
cell_points = cell_weight
              * min(1, best_valid_median_seconds / observed_median_seconds)
```

The TTFT cells are 1K, 2K, 4K, 8K, and 16K with weights 5, 5, 7, 8, and 10.
The TPOT cells are 1K and 8K with weights 10 and 15. Every cell generates 128
tokens. A cell gets zero when its exact prompt length, output budget, success
rate, warm-up/repeat policy, metric, or stability requirement is invalid.

The midterm profile requires one warm-up, five measured samples, the median as
the official value, and CV at or below 10% per latency metric. Raw samples and
environment evidence must still be archived even though the compact submission
contains their aggregate.

Because the reference population changes, scores are recomputed whenever a new
valid PR joins a round. The leaderboard publishes named frozen snapshots; the
snapshot at the grading deadline is authoritative. This avoids two bad
outcomes: the first slow submission receiving an artificial 100, and vLLM
permanently suppressing a student implementation that genuinely exceeds it.

## Long-context bonus: 0–10

32K is the base boundary and earns zero bonus. Verified context above 32K earns
logarithmic progress toward 10 points:

```text
context_bonus = 10
                * clamp(
                    log2(max_verified_prompt / 32768)
                    / log2(262016 / 32768),
                    0,
                    1)
```

The pinned checkpoint declares 262,144 native positions. The scoring ceiling
is therefore 262,016 prompt tokens after reserving the required 128 output
tokens. Approximate milestones are:

| Verified prompt | Bonus |
|---:|---:|
| 32,768 | 0.00 |
| 65,536 | 3.33 |
| 131,072 | 6.67 |
| 262,016 | 10.00 |

The staircase first probes 32,640 prompt tokens as a non-scoring diagnostic for
services with a 32,768 total-sequence limit. Every scoring length above the 32K
bonus start runs six cases: early/middle/late retrieval, multi-hop, revision,
and aggregate, all with the complete 128-token output. Below the native ceiling
the evaluator also records the first larger capacity failure, then checks
`/health` and a small generation request. An OOM or explicit admission failure
is an acceptable boundary only when the service recovers; an OOM in a base
performance cell remains an unexpected failure.

## Multi-request bonus: 0–10

The optional serving track sends 32 independent 1K/128 requests through the
same public endpoint in closed loop at concurrency 4 and 8. Queueing is inside
the timing boundary. Each cell contributes:

```text
1 support point
+ 4 * min(1, observed_correct_goodput / best_valid_goodput)
```

`correct_goodput` counts only completion tokens from successful, functionally
correct requests divided by the client-observed batch makespan. A cell is valid
only when all requests succeed and pass correctness, Jain fairness is at least
0.95, no fallback occurs, and the service remains healthy. It also has
candidate-relative tail guards:

- p95 TTFT ≤ `1.5 × concurrency ×` that candidate's 1K single-request TTFT;
- p95 TPOT ≤ `3 ×` that candidate's 1K single-request TPOT.

The best valid same-round goodput receives the four performance points for the
cell. A serial queue may still prove interface support, but it will not be
competitive on goodput. Missing multi-request support simply earns zero bonus
and does not invalidate the base score.

## Multimodal capability badge

The checkpoint contains a real 27-layer vision tower, so image input is tested
as an integrated capability rather than inferred from `config.json`. This track
is an independent v1 overlay with zero leaderboard points; adding points later
requires a new leaderboard contract and a newly frozen cohort.

The public generator creates four deterministic 448×448 RGB PNG cases using
only the Python standard library: seven-segment OCR, spatial color lookup, bar
arithmetic, and object counting. The hidden generator creates two private
variants of each category from a teacher seed. Every PNG, cases JSONL, and
manifest is SHA-256 verified. A supported service must pass all 4 public and all
8 hidden exact-answer cases to receive `multimodal-ready`.

```bash
python3 benchmarks/qwen38_4090/evaluation/generate_multimodal_cases.py \
  --output-dir /tmp/apxinf-mm-public

python3 benchmarks/qwen38_4090/evaluation/run_multimodal.py \
  --base-url http://127.0.0.1:8001 \
  --suite-dir /tmp/apxinf-mm-public \
  --implementation-name my-apxinf \
  --implementation-revision FULL_COMMIT_SHA \
  --backend apxinf-native \
  --output /tmp/apxinf-mm-public-report.json
```

A text-only implementation must report `multimodal=false` and reject the probe
with a 4xx/501 `unsupported_capability` error. Returning 200 after ignoring the
image, returning 500, or using a hidden fallback fails the protocol. Integrated
image E2E latency and VRAM are diagnostics and are not mixed with pretokenized
text TTFT/TPOT because server-side media preprocessing is intentionally inside
this capability boundary.

## Course-grade mapping

The leaderboard displays `base_score / 100`, `bonus_score / 20`, and their sum
out of 120. The automated course component remains capped at 80 points:

```text
automated_course_points = min(80, 0.8 * eligible_leaderboard_score)
course_grade_without_workflow_bonus
                        = automated_course_points + PR_review_points

final_course_grade      = min(100,
                              course_grade_without_workflow_bonus
                              + workflow_innovation_bonus)
```

The leaderboard bonus can therefore recover base-score deficits, but it cannot compensate
for a failed correctness/reliability gate and cannot make the automated course
component exceed 80. PR review contributes the remaining 20: tests and
negative controls 8, interface/error handling 4, reproducibility 4, and
analysis/decision quality 4. The separately reviewed workflow-innovation bonus
is 0–5 course points, has no leaderboard effect, and cannot make the final
course grade exceed 100.

## One-week course schedule

The course uses Asia/Shanghai time. Students submit an immutable PR SHA and
public artifact before 19:00 on day 4. The teacher freezes the cohort, runs all
entries plus the required vLLM control from clean checkouts, and publishes one
named midterm leaderboard snapshot after the unified evaluation completes.
Changes after the cutoff belong to the final snapshot.

The final PR SHA and detailed `REPORT.md` are due before 19:00 on day 7. The
report must connect the submitted implementation to its baseline, hypotheses,
correctness, performance, efficiency, negative results, limitations, rollback,
and exact reproduction commands. The complete policy is
`course-policy-v1.json`.

## Cohort scoring

Student repositories contain no teacher implementation measurements. The
public tests use synthetic numbers to prove the scorer's algebra and gates.
Actual public calibration artifacts are generated by `run_evaluation.py` on
the grading machine; official artifacts additionally include the frozen hidden
set and required vLLM control.

```bash
python3 benchmarks/qwen38_4090/evaluation/score_submission.py \
  --profile midterm_leaderboard \
  --require-official-control \
  --control-submission teacher-vllm.json \
  --submission pr-001.json \
  --submission pr-002.json \
  --output midterm-snapshot.json
```

An artifact with one measured repeat is bring-up evidence only. The official
midterm profile rejects it unless every cell has one warm-up, five measured
repeats, and CV at or below the frozen limit.

## MFU and BWU

For W4A16 there is no honest single operation peak representing the entire
model. The path combines quantized weight loads and dequantization, BF16 Tensor
Core work, recurrent layers, attention, and elementwise kernels. The public
script therefore reports explicitly named diagnostics:

1. `estimated_mfu_bf16_equivalent_pct` uses the frozen dense-equivalent FLOP
   proxy and the RTX 4090 dense BF16 Tensor Core peak with FP32 accumulation.
2. `minimum_model_bwu_pct` uses the frozen minimum model-byte estimate. It is a
   lower-bound model-byte proxy, not measured HBM traffic.
3. `profiled_bwu_pct` is emitted only from phase-scoped Nsight Compute DRAM
   read/write bytes and kernel elapsed time.

```bash
python3 benchmarks/qwen38_4090/evaluation/compute_efficiency.py \
  --submission submission.json --output efficiency.json
```

`tensor_pipe_active_pct` and `nvidia-smi utilization.memory` remain telemetry;
neither is renamed to MFU or converted into bandwidth by multiplication with
the nominal peak. Proxy values above 100% trigger a counting/timing-boundary
audit rather than being clipped.

## Release boundary

The released student bundle contains the text contract, multimodal capability
overlay, assignment, interface, public data generators, runners, scorers,
efficiency calculator, schemas, and synthetic/negative-control tests. It
contains no teacher implementation, private kernels, hidden generators or
seeds, model/host paths, or measured teacher results.

Teacher-side release metadata content-addresses the starter commit, evaluator
bundle, model files, public/hidden/context manifests, and vLLM trajectory
reference. Cohort execution uses detached worktrees at full PR SHAs and writes
a separate provenance hash for every snapshot. Container/driver and two-machine
drift pilots are frozen with the midterm environment; they are operational
round metadata rather than a reason to change this workload contract.
