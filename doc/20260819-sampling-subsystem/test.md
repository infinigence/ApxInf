# Sampling Subsystem Test Plan

Date: 2026-08-19
Status: Implemented and passing

## Test layers

### 1. Pure semantic tests

Source: `crates/apxinf-core/src/sampling.rs`

These tests run without CUDA and define the authoritative behavior:

| Area | Required behavior |
|---|---|
| Logits view | Explicit/final row is bounds-checked and vocabulary-checked |
| Greedy | Maximum adjusted logit; lowest token ID wins ties |
| Greedy logprob | Stable for very large logits and normalized over vocabulary |
| Repetition | Negative repeated logits multiply; non-negative logits divide |
| Frequency/presence | Prompt and generated-token counts affect later draws |
| Top-k | `k=1` matches greedy selection |
| Top-p | Tail outside the retained cumulative mass cannot be selected |
| RNG | Philox reference vector, same-key reproducibility, sequence isolation |
| Validation | Invalid parameters and prompt IDs fail explicitly |
| Invalid logits | NaN/negative-infinity-only rows fail explicitly |
| Normal RNG | Reproducibility, stable allocation, distribution sanity |
| Half outputs | f16 and bf16 values match the f32 reference within tolerance |

Run locally:

```bash
cargo test -p apxinf-core --lib sampling::tests
```

### 2. CPU/CUDA differential tests

Source: `crates/apxinf-cuda/src/tests/sampling.rs`

These tests require a CUDA machine and compare backend implementations rather
than checking only whether a kernel launches:

- 32,768-token multi-block greedy selection and tie handling;
- stable greedy log-probability for tied `f32::MAX` logits;
- five sequential random draws with prompt/generated history, all penalties,
  temperature, top-k, and top-p;
- f32, f16, and bf16 logits;
- exact token equality and log-probability tolerance;
- f32 CPU/CUDA normal value agreement and distribution; and
- direct f16/bf16 normal-output conversion checks.

Run on Thor:

```bash
APXINF_CUDA_ARCH=sm_110 \
APXINF_CUDA_ARCH_CUTLASS=sm_110a \
cargo test -p apxinf-cuda sampling -- --test-threads=1
```

### 3. Generation integration tests

Source: `crates/apxinf-model/tests/unified_llm_input.rs`

A recording mock model verifies orchestration independently of model math:

- the compatibility API follows the existing greedy prefill/decode sequence;
- image data is consumed once during prefill and never enters decode;
- text-only rejection occurs before prewarm or forward;
- partial `GenerationOptions` exposes request sampling and log-probabilities
  without a model-specific hook;
- `AutoModel` loads `generation_config.json`, while explicit request fields
  override its defaults;
- callbacks receive the same `GeneratedToken` values as the output;
- zero-token generation performs no model work;
- any configured EOS ID stops before another decode;
- invalid sampling parameters fail before reset/prewarm/forward; and
- `LoadedModel` and direct `LlmTrait` calls share the same pipeline.

Run locally or on Thor:

```bash
cargo test -p apxinf-model --test unified_llm_input
```

### 4. VLA contract and real-model tests

The model-neutral unit tests in `crates/apxinf-model/src/vla/mod.rs` verify that
an observation no longer owns generation noise and that `Provided` and
`Generate` requests remain distinct.

The offline Python policy tests verify the L2 routing contract: absent noise
uses the model's internal path, keyword and observation noise are forwarded
exactly, keyword input wins, invalid shapes are rejected, and an explicitly
installed host sampler remains supported.

The PI0.5 smoke example adds hardware checks for stable shapes, same-key
reproducibility, CPU-reference versus device-generated latent parity, and
sequence isolation:

```bash
APXINF_CUDA_ARCH=sm_110 \
APXINF_CUDA_ARCH_CUTLASS=sm_110a \
cargo run -p apxinf-model --example pi05_auto_smoke --features cuda -- \
  /home/wwxq/Projects/models/pi05_libero_base 32
```

### 5. Real LLM/VLM regression

Use a fixed checkpoint, prompt, image fixture, and token count. Compare token
IDs against an untouched build from the same commit and checkpoint, not a
golden generated by a different model.

Text:

```bash

APXINF_CUDA_ARCH_CUTLASS=sm_110a \
cargo run --features cuda -- generate \
  --model /home/wwxq/Projects/models/nvidia/Cosmos-Reason2-2B \
  --prompt 'What is a robot?' --max-tokens 10 --no-eos-stop \
  --device cuda --dtype bf16
```

VLM fixture:

```bash

APXINF_CUDA_ARCH_CUTLASS=sm_110a \

  /home/wwxq/Projects/models/nvidia/Cosmos-Reason2-2B
```

## Tolerances

| Check | Threshold |
|---|---:|
| CPU/CUDA categorical token ID | Exact |
| CPU/CUDA selected-token logprob | Absolute error `< 3e-5` |
| CPU/CUDA f32 normal | Maximum error `< 2e-5` |
| f16 normal versus f32 reference | Per element `<= 0.002` |
| bf16 normal versus f32 reference | Per element `<= 0.02` |
| Normal sample mean, 100k values | Absolute value `< 0.02` |
| Normal sample variance, 100k values | Absolute error from one `< 0.03` |
| Same-key reproducibility | Exact |
| Baseline LLM/VLM token IDs | Exact |

## Full integrity gate

The release candidate must pass the entire CUDA workspace, because changing
backend logits or synchronization can regress unrelated model paths:

```bash
APXINF_CUDA_ARCH=sm_110 \
APXINF_CUDA_ARCH_CUTLASS=sm_110a \
cargo test --workspace --features cuda -- --test-threads=1
```

Portable checks:

```bash
cargo test -p apxinf-core --lib
cargo test -p apxinf-model --lib --test unified_llm_input
cargo check --workspace --all-targets
git diff --check
```

On a host without CUDA, `cargo check` covers all portable targets, while the
CUDA-linked test executable must be built and run on the NVIDIA device.

## Performance regression gate

Correctness tests do not replace profiling. For a performance-sensitive
change, capture a release Nsight trace and verify:

- no vocabulary-sized device-to-host copy per token;
- exactly one compact sample-result transfer per token;
- no CUDA allocation in the per-token loop;
- no host synchronization between graph replay and sampler launch;
- sampler buffer addresses remain stable across draws; and
- greedy/random TPOT does not regress beyond the agreed benchmark tolerance.

## Change checklist

When modifying the subsystem:

1. update CPU semantics first or update CPU and CUDA in the same change;
2. add an independent hand-computed semantic case, not only CPU/CUDA parity;
3. run all three logit dtypes;
4. test multiple sequential draws so generated-token history is exercised;
5. run the unified generation integration suite;
6. run PI0.5 seeded/provided parity if normal generation or VLA ownership
   changes;
7. compare a real LLM and VLM against the untouched baseline; and
8. run the complete Thor workspace gate.
