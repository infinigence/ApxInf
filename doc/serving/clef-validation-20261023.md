# Clef serving 验证记录

日期：2026-10-23。设备为 Apple M4、16 GiB 统一内存。
本轮验证结果未达到 Clef 在 ApxInf 内的正向 serving 验收。
参考服务能否启动、ApxInf 是否执行决策头、业务请求是否成功是不同的检查。

## 当前接入边界

ApxInf 的 `apxinf-serve` 尚无 Clef provider，也没有 `/v1/systemone` 路由。
实际 CLI 指定 `--provider clef` 返回退出码 2，并列出当前支持的 provider。
当前请求和事件描述聊天生成，不包含 Clef 的 typed questions 和概率结果。
把 Clef 的语言骨干当作聊天模型运行不构成 Clef 支持。

独立模型分支 `origin/codex/metal-clef` 的检查基线为 `2497800a887428a60ce9060b053430f814646056`。
该分支提供第一方 `ClefRunner` 和决策 schema，但没有 HTTP serving。
其原生实现仅支持文本，输入上限为 4096 token。
该限制不能用本地模型包参考服务的 16K／图片能力替代。
本轮没有合并该模型分支，也没有提交其模型或内核修改。

## 本地参考对象

模型为 `mlx-community/clef-flash-4bit`，本地标记 revision 为 `b5adbe2c3a95200d4bf04a0727c8ec457157d5e1`。

全部 safetensors 文件合计 6193757576 字节。
模型包附带的 `clef_mlx.py` 提供独立参考服务；它不是 ApxInf 的 worker。
本轮没有修改或导入该依赖的实现代码到 ApxInf。

观察程序检查监听进程身份，并在进程组回收后释放锁。
配置为 loopback、16384 上下文、1 MiB 请求体，并显式关闭截断。
模型、四位量化配置及 BF16 决策头保持不变。

## 已修复的错误接入风险

检查发现，通用文本 worker 原先仅检查自定义代码配置，没有检查独立决策头文件。
Clef 保留普通 Qwen3.5 配置名，因此可能进入骨干聊天加载路径。
原创 CPU 回归在两个决策头标记上均复现错误，失败信息为 `The bundle reached model identity hashing.`。

现在，文本 worker 在身份摘要与 MLX 加载前拒绝包含任一标记的模型包：

- `joint_head_config.json`。
- `joint_head.safetensors`。

错误码沿用 `model_unavailable`，说明文本 provider 不支持决策头。
普通 `qwen3_5` 文本包仍能进入原有身份校验路径。
实际本地 Clef 模型目录也通过了拒绝检查，且没有导入 MLX。
文本 worker 的 37 项 CPU 测试通过。
全量 Python serving 测试运行 325 项，318 项通过，7 项跳过。
仅安装 NumPy／Pillow 的独立 CPU 环境运行 325 项，305 项通过，20 项跳过。
该修复保证明确拒绝，不增加 Clef 正向 serving 能力。

后续正向接入需要独立决策请求／概率结果协议、明确 provider 和对应 HTTP 路由。
它还需要完成准备计数、输入上限、执行所有权、取消边界、资源结算及实机请求矩阵。
不能把概率结果伪装成生成 token，也不能把参考服务绕过 ApxInf 的执行算作验收。
