# FlashInfer Cake GDN prefill, vendored

Source: https://github.com/flashinfer-ai/flashinfer, `csrc/gdn/cake/cuda/`.
Licence: Apache-2.0 (repository-wide; the per-file headers carry the notice).

Two files are vendored verbatim apart from one documented patch:

  gdn_prefill_generated.cuh
  cake_gdn_prefill_dvsplit_initial_f16io_gatepipe4_ac92807e7ba4.cu

They are machine-generated by a "Cake" generator that is not in the FlashInfer
repository, so they cannot be regenerated with different schedule constants --
only read, patched and compiled. Their only includes are `cuda_bf16.h`,
`cuda_fp16.h`, `cuda_fp8.h` and `math_constants.h`: no CUTLASS, no CuTe, no
TVM-FFI, no Python. That is what makes them usable from our Rust FFI.

## Why this variant

Our GDN has 16 q/k heads and 48 v heads. Neither 48 nor the group size 3 is a
power of two, which rules out every specialized variant and leaves the
head-generic ones (`NUM_O_HEADS_LOG2 = -1`, `HEAD_GROUP_LOG2 = -1`). Of those,
only FP16-I/O variants exist -- the head counts are baked into the generated
source as literals, so flipping a `#define` does not produce a BF16 build.
FlashInfer's own manifest routes our `hq16_hv48` shape to these same files.

FP16 I/O was measured against real activations before committing to it: the
widest GDN tensor peaks at 33 and `v` -- what a delta-rule update accumulates
into, so the first thing that would overflow -- peaks at 5.66, against FP16's
65504 ceiling. See `devlocal/qwen38-nvfp4/reports/flashinfer-gdn-feasibility.md`.
The recurrent state stays FP32 regardless.

## The one patch: APXINF_GDN_LOG_GATE -- present but OFF

The stock kernel takes `gate` as a linear-space decay and converts it with

    asm volatile("lg2.approx.ftz.f32 %0, %1;" : "=f"(_log2_N) : "f"(gate_val_N + 1e-10f));

at six sites. Our pipeline produces `g` in natural-log space, so feeding it
`exp(g)` for the kernel to take `lg2` of again looks like a wasteful round
trip. Defining `APXINF_GDN_LOG_GATE` replaces each site with
`_log2_N = gate_val_N * 1.4426950408889634f`, consuming `g` directly.

**It is deliberately left undefined, because enabling it is wrong here.**

This variant is `gatepipe4`: gate loads are prefetched four deep. At a single
chunk the pipeline reaches past the end of the sequence and picks up
uninitialized slots. `lg2(garbage + 1e-10)` collapses whatever it finds into a
finite log, which the decay then treats as harmless. A multiply by log2(e)
preserves the garbage and scales it.

Measured, at 16 q-heads and 48 v-heads against our own chunk scan:

| seq | state RMS ours | state RMS FlashInfer, patch ON | patch OFF |
| --- | --- | --- | --- |
| 64  | 4.262e-2 | **2.657e26** | 4.262e-2 |
| 128 | 4.094e-2 | 4.094e-2 | 4.094e-2 |
| 512 | 4.096e-2 | 4.095e-2 | 4.095e-2 |

Only the single-chunk case breaks, because longer sequences have real chunks
to fill the pipeline with. Worth recording how nearly this slipped through:
the ruined state pointed the *right direction*, so **cosine scored 0.999988 on
it**. Only a magnitude assertion caught it. Any comparison written against this
kernel must check magnitudes, not just cosine.

So the caller exponentiates: pass `alpha = exp(g)`. That costs one `exp` per
token per head, which is small beside the kernel itself, and the macro stays in
the file documenting why the shortcut is unavailable.

## Build requirements

    -gencode arch=compute_110a,code=sm_110a

`-arch=sm_110a` alone is wrong: nvcc also emits `compute_110` PTX and ptxas
rejects tcgen05 for the non-`a` target.

Resource fit on Thor is real but tight:
  registers      168 x 384 = 64512  <= 65536
  shared memory  226048 + 1024 = 227072 <= 232448   (4.9 KB margin)

The kernel is `__launch_bounds__(384, 1)`, i.e. one CTA per SM by design, and
persistent: `grid_x = min(SM_count, total_tiles)`. Thor's 20 SMs are fine --
measured 0.427 ms per call at 2048 tokens on our 16/48 head shape, against
2333 ms for 48 layers of our own scan.
